# CalNutriFit upgrade — 20 October 2026

## Implemented in this increment
- Dedicated My Profile and Progress routes, using the existing authenticated journal. Profile/goals/preferences editing reuses the existing validated flows.
- Weight entry in kg/lb, canonical kg storage, preferred unit persistence, exact conversion without writing rounded display values, dated edits and deliberate deletion. Fixed the backend omission that previously failed to delete removed weight records.
- Weight graph with 7/30/90-day, six-month, one-year and all-time filters, actual measurement dates, goal line, accessible table and range statistics. Weekly endpoint trend only appears with at least three measurements spanning seven days.
- Optional label-entry fields for all 13 requested vitamins and 11 minerals, plus sugar and saturated fat. Portion and recipe calculations preserve available values; missing values are not zero-filled. No old catalog micronutrients were promoted to verified data.
- Dedicated Nutrients route separates known food and actual supplement contributions, displays missing-item counts, and shows RDA/AI comparisons for all 24 requested vitamins/minerals and supported UL comparisons. Magnesium UL applies only to supplement contributions. No deficiency diagnosis.
- Personal supplement products saved independently of actual intake; reuse requires an explicit intake confirmation. Dose nutrient snapshots survive reload and are independent of the saved product.
- Custom workout entry: name, notes, active minutes, body weight, sets/reps, transparent MET estimate or manual calorie override. Reuse previous custom activity descriptions. No AI interpretation is claimed.
- Provider-aware account controls: current-password reauthentication before password change for email accounts; external-provider explanation for OAuth-only accounts; sign out other refresh sessions. Existing export retained.
- Analytics CSV export for the selected date range; weight display respects units. Missing measurements remain blank in exports.
- Background refresh when returning online/focusing an idle journal, with race protection against a concurrent local save. Settings fields reject changes made from an obsolete snapshot.

## Architecture and persistence
No new database tables or destructive migrations. Existing RLS-protected tables are reused:
- food_entries.food_item_data.calnutrifit stores full food/portion nutrition snapshots, including optional details.
- supplement_entries.supplement_data.calnutrifitDetails stores per-serving label quantities; quantity scaling happens once on read/write.
- workout_entries.exercise_data retains custom description, MET, body weight at logging, and calorie method.
- user_settings.settings.calnutrifit.supplementProducts holds saved personal products; preferences retain measurement units.
- weight_logs remains canonical kg with the existing user/date uniqueness constraint.
Existing historical calorie estimates are not recalculated when profile weight changes. Existing Nutrio fields are preserved. These extensions rely on the existing JSON columns; no admin keys are sent to the browser.

- https://ods.od.nih.gov/factsheets/Calcium-HealthProfessional/

- https://ods.od.nih.gov/factsheets/VitaminC-HealthProfessional/
- https://ods.od.nih.gov/factsheets/VitaminD-HealthProfessional/
Only age 19+ nonpregnant/nonlactating general adult categories are implemented; the individual-guidance flag disables these targets. Vitamin C assumes a nonsmoker. Remaining adult references use the Health Canada vitamin and element tables. Form-dependent upper limits are not evaluated when the required nutrient form is unavailable; sodium CDRR is distinct from a UL. These are dietary references, not a personalized medical assessment or supplement prescription. Label-entered nutrition is user reported, not independently verified.

- Supplement reminders and label photos remain open. Product editing, brand/type/notes, daily/weekly schedules, skipped status and editable intake history are implemented. Archiving legacy routines preserves historical calorie contributions.
- AI workout/natural-language interpretation is not enabled; manual custom workouts remain usable. Expanded licensed activity demonstrations, intensity/distance fields and further exercise classification remain open.
- Progress photos, avatar management and historical target snapshots remain open. Optional body measurements and private health notes are implemented.
- Weight history renders the chosen range without server pagination; large-history scalability remains open. Full browser/accessibility audits, backup/recovery administration and production field metrics remain unverified.
- Full two-device simultaneous browser test and post-deployment authenticated refresh are not substitutes for the completed adapter sign-out/sign-in test; they remain separate checks.
No claim is made that every acceptance criterion in the full upgrade specification has been met.

## Cross-device record protection — follow-up
Implemented conditional database updates/deletes for food, supplement, workout, recipe and goal rows using the exact values loaded by that journal. Snapshots are retained in a WeakMap and are not exported or stored in browser storage. A competing edit or removal produces a conflict message rather than overwriting the newer row. Weight changes/deletes compare the previous weight/date/id; new dates use insert rather than an upsert that could replace an unseen measurement. All next weights are validated before any network mutation.

Changed files: src/backend.ts, src/mutation.test.ts, scripts/check-upgrade-persistence.mjs. No new database tables, migration, service or environment variables. Existing RLS and the unique user/date weight constraint remain in effect.

Validation: 76 automated tests passed. Production build passed. Live disposable-account tests used two independently loaded journals for each of foods, goals, recipes, workouts, supplements and weights: stale update and delete both failed, newer values remained intact, and fixture cleanup completed. The persistence and stale-settings checks also passed.

Limitations: these conditional writes protect individual rows; they do not make a multi-record save atomic. Saves that span tables can still partially commit before a later operation fails. Retry-safe inserts and full transaction support still require backend work. Simultaneous browser/device UI sessions were not exercised by the adapter test.
